# DeepWrite 专业机制拆解与 InkForge 长篇优化报告

日期：2026-10-09。优先目标：长篇稳定性与创作质量。

DeepWrite 研究基线为提交 `69858fb1ae60a1fcc84b71122f945b1c86949049`，该快照源码版本为 `1.6.308`。InkForge 本轮基线为 `0.33.2`，正文提示词由 `prose-2.0.0` 升级到 `prose-2.1.0`。以下区分已有能力、本轮完成的代码修改和后续建议；后续建议不代表已经实现。

## 1. 核心判断

DeepWrite 最有参考价值的地方，是把创作过程中的上下文、工具权限、修改提案、事实来源和恢复状态组织成可以验证的工作流程。它给智能体提供了持续做事的条件，也给作者保留了审阅和追查结果的入口。

InkForge 已经具备适合中文长篇的另一组基础：按章节时间过滤证据、区分作者设定与已发生事实、候选正文和正式正文分离、正文接纳与记忆结算分阶段执行。适合你的优化方向，是在这些基础上补齐模型请求和恢复的边界，让长篇写作不因上下文裁剪、连接中断或错误的完成判定失去可靠性。

本轮已完成这一部分工程优化。它改善了生成结果的完整性、可恢复性和方法执行条件；文学质量是否提高，仍需同模型、同素材的实际作品评测。

## 2. DeepWrite 做得专业的八个方面

### 2.1 按创作职责组织产品和上下文

人物、剧情、大纲、正文、分节写作各有职责。界面的作品导航、智能体过程和实际文稿同时可见，作者可以理解“现在处理哪个对象、依据哪些资料、结果落在哪里”。这比只提供输入框和生成按钮更适合持续创作。

源码中的 `planWorkspaceRun` 将目标、工具、系统提示、当前消息和上下文策略组合成运行计划。公共内核处理运行机制，各创作阶段决定内容和能力范围。这种职责分配使模型选择、工具协议和恢复机制可以共享，任务配方仍能保持不同。

对 InkForge 的启发：你已经有规划、生成、审校、记忆服务，不需要为了模仿产品外观迁移到 Electron/Vue。后续应继续把导演的大流程拆为明确阶段，减少每个阶段自行实现重试和持久化。本轮将正文接收与恢复提取到 `app/writing/prose_recovery.py`，预算与回执判断提取到 `app/core`，是沿这个方向做的小范围落地。

来源：[工作空间运行计划](https://github.com/swjybky/deepwrite/blob/69858fb1ae60a1fcc84b71122f945b1c86949049/packages/pi-runtime-adapter/src/workspace-run-plan.ts)、[项目产品说明](https://github.com/swjybky/deepwrite/blob/69858fb1ae60a1fcc84b71122f945b1c86949049/README.md)。

### 2.2 上下文有预算、保留原则和失败回滚

DeepWrite 的上下文预算同时考虑模型窗口、输出空间和安全余量。达到工作预算一定比例时先精简旧快照和可重新读取的工具内容，再对较早的对话做结构化摘要。近期消息与完整工具调用关系有保留规则；摘要失败时保留原状态。

专业价值在于明确哪些信息可以压缩、哪些必须恢复到原始来源。用户原话、当前约束与技能不能随意截掉一半。摘要用于保存决定和进度，作品正文、设定和素材仍从源文件读取。恢复失败也不能伪造缺失内容。

InkForge 的主要上下文来自作品状态与按章证据视图，而非无限增长的工具对话。因此，直接复制一个默认 160k 的会话摘要系统不合适。你的本地模型可能只有较小窗口，最需要先解决完整请求预算和必需约束的完整性。本轮统一预算估算，约束超限时明确停止；低优先级 Skill 以完整方法为单位取舍。

来源：[上下文压缩设计](https://github.com/swjybky/deepwrite/blob/69858fb1ae60a1fcc84b71122f945b1c86949049/docs/context-compaction.md)、[预算计算实现](https://github.com/swjybky/deepwrite/blob/69858fb1ae60a1fcc84b71122f945b1c86949049/packages/pi-runtime-adapter/src/kernel/context/budget.ts)。

### 2.3 修改提案与真实保存存在边界

DeepWrite 有差异审阅、提案处理和底层版本检查。作者能看到具体修改，旧输入产生的结果也不能任意覆盖较新的文稿。这将“模型建议修改”和“系统成功保存”拆成了不同状态。

对创作质量的实际意义是保护取舍过程：好稿不因迟到的旧结果被替换，作者可以比较多个方向，否决的内容也不会因为对话摘要而被误认为已采用。

InkForge 已有候选稿、修订版本、插入时原文比较和数据库乐观并发控制。这些机制应继续作为正式正文的边界。本轮为生成结果增加 `completion_state`：正常完成与仍需复核的候选分开；导演的流恢复检查点也不直接进入正式正文或记忆。

需要核实的细节：DeepWrite 的 README 强调审阅，但这个源码快照的默认设置包含 `permissionMode: auto-approve`、跨阶段自动批准和自动保存。存在审阅机制，与默认每次都等待人工批准，是两个不同结论。

来源：[提案协调代码](https://github.com/swjybky/deepwrite/tree/69858fb1ae60a1fcc84b71122f945b1c86949049/apps/desktop/src/renderer/src/composables/proposal-coordinator)、[默认设置](https://github.com/swjybky/deepwrite/blob/69858fb1ae60a1fcc84b71122f945b1c86949049/packages/contracts/src/general-settings.ts)。

### 2.4 连续性状态拥有稳定引用

DeepWrite 的长篇连续性账本关联章节、人物状态、交接信息和伏笔变化。账本审计会核对记录引用的章节与文件清单是否仍存在、是否与索引一致。长期状态因此有来源和归属，不只是会话里一句“前面发生过什么”。

但也不能把它描述成完全不可变的事实数据库：该快照的 v4/v5 账本审计明确允许关联文本直接编辑，主要检查身份和路径引用。源文件、账本记录和当前内容之间仍有不同的验证职责。

InkForge 在这一方向已有值得保留的机制：正文证据逐字校验、正文哈希绑定、事实有效时间与替代关系、修改后使后续记忆失效。建议继续强化这些能力，不把模型摘要提升为新的权威源。

来源：[连续性账本审计](https://github.com/swjybky/deepwrite/blob/69858fb1ae60a1fcc84b71122f945b1c86949049/apps/desktop/src/utilities/long-ledger-v4-audit.ts)。InkForge 对应实现：`app/story/temporal_context.py`、`app/story/memory_integrity.py`、`app/review/memory_settlement.py`。

### 2.5 长任务以单元、依赖与持久化回执恢复

DeepWrite 的整书拆解具有独立任务状态、单元状态和输出回执。恢复时重新验证来源和目标；一个单元即使被标记为完成，若对应回执缺失或损坏，也会被转为冲突状态。它不会只相信进度条上写着“完成”。

这体现了一个实用原则：恢复必须以已经保存并可核验的结果为依据。长任务有阶段性产物，下一阶段只消费有效产物，才可以避免从头重来以及重复执行写入。

InkForge 本轮落地了适合正文流的对应机制：约每两秒保存接收片段，在断线、暂停、失败与完成时立即保存；完整消息、模型及生成设置形成输入哈希。只有同一输入才能复用结果。同章保留最多 32 个调用回执，让后续分场恢复时可以复用前序已完成结果。章完成后清理这组流检查点。

来源：[拆解任务恢复](https://github.com/swjybky/deepwrite/blob/69858fb1ae60a1fcc84b71122f945b1c86949049/apps/desktop/src/utilities/long-book-decomposition/job-recovery.ts)。

### 2.6 分批规模考虑输出容量

DeepWrite 的拆解批量预算会估算单个阅读卡、事实条目、伏笔和审查问题所需输出。思考过程与可见回答共享单次输出限制，因此提高思考强度时，相同任务可能需要更小批次。

专业价值是识别另一种失败：材料可以放进输入窗口，要求交付的结果却装不进回答。反复重试同样的大 JSON，常常只会再次被截断。

InkForge 本轮解决了初次结构化请求、JSON 修复和正文续补的剩余空间计算。重试加入新的纠错指令后，输出预算会重新计算，不能机械加大。保留全部输入，如果连最小有效输出空间也没有，则在模型调用前停止。

本轮尚未实现全书规划按输出条目自动拆批。这是下一步适合继续借鉴的机制：先为每卷、每个角色卡或每批事实定义最小独立交付，再计算批量大小，最后验证总数、顺序与跨批引用。

来源：[输出预算与批量计算](https://github.com/swjybky/deepwrite/blob/69858fb1ae60a1fcc84b71122f945b1c86949049/packages/contracts/src/long-book-decomposition/output-budget.ts)。

### 2.7 分析结论必须能定位到原文

DeepWrite 的拆书证据检查从确定的章节或段落范围验证逐字摘录。章节身份与段落归属由源资料决定，不能让模型自行编造。改写、拼接或从其他章节摘取的证据不能冒充当前单元的有效来源。

对 InkForge，最应持续推进的是“草稿证据”和“权威证据”双向核对：审校必须引用草稿中的真实片段，再指出具体哪条事实与之冲突。没有来源的严重问题只能待复核。这样可以减少模型因为个人文风偏好乱改稿，也能降低长篇中错误记忆的扩散。

你已经有 `evidence_audit.py` 与正文绑定的记忆提交。当前应把它们纳入更多端到端场景和评测案例；无需新建一个与现有事实源竞争的记忆系统。

来源：[拆书证据验证](https://github.com/swjybky/deepwrite/blob/69858fb1ae60a1fcc84b71122f945b1c86949049/apps/desktop/src/utilities/long-book-decomposition/evidence-validation.ts)。

### 2.8 工程边界由检查工具执行

DeepWrite 的页面渲染层有依赖检查，禁止直接导入文件系统、数据库和模型运行时等能力；项目还提供类型检查、构建验证和针对状态恢复的测试。边界因此能被自动检查，而不仅存在于架构图里。

InkForge 已有领域层依赖检查、路由唯一性、资源存在性、版本一致性和跨平台 CI。本轮把 5 个真实流读取行为测试接入已有静态检查入口，覆盖逐字节 UTF-8、CRLF、多行事件数据、服务器错误、提前 EOF，以及完成确认后无需等待连接关闭。

这一点比增加测试数量本身更有价值：测试可以复现会丢稿或误报完成的边界。模型文学判断仍需要另一套作品评测。

来源：[渲染层依赖检查](https://github.com/swjybky/deepwrite/blob/69858fb1ae60a1fcc84b71122f945b1c86949049/tools/check-renderer-boundary.mjs)、[项目检查入口](https://github.com/swjybky/deepwrite/blob/69858fb1ae60a1fcc84b71122f945b1c86949049/package.json)。

其中三个问题会直接损害长篇创作条件：关键规则被裁掉、未完成响应被当成完成、恢复时丢失已写片段。另一个问题会损害阅读体验：续补把段落节奏压成一整段。这些均已通过代码和回归测试处理。

## 4. 本轮代码改动如何工作

### 4.1 一个完整请求预算

`app/llm/budget.py` 提供共享估算与预算对象。请求预算包含内容估算、每条消息的近似开销、输出预留和安全余量。预览展示完整请求是否能容纳；网络入口执行同一规则。

续补追加已收到正文，JSON 修复追加纠错要求，它们都必须重新计算。可调整的是输出 allowance；作者要求、事实材料和已保存正文不能被静默删掉。如果剩余空间不足以提供最小有效输出，抛出明确的预算错误，保留原材料。

中文字符不再按原先的折扣估算，emoji 与其他非 ASCII 字符也不再按 ASCII 成本计算。这里仍使用近似估算，未接入各模型精确 tokenizer，也未自动识别实际模型窗口。上限必须与模型能力匹配；界面将数据标记为 `estimated`。

### 4.2 模型完成确认与正文完整性分开判断

`app/llm/completion.py` 提供 `StreamOutcome`，记录完成标记和原因。模型在 HTTP 200 的响应流内部返回错误时，仍会视为失败；连接关闭而没有完成标记，也不会被当成成功。

`length/max_tokens` 表示输出 allowance 耗尽，即使最后一个字符是句号也需要处理。导演会有界续补；普通生成最多进行原有的两轮修复，仍未收束时返回 `needs_review`，供作者保留并复核。句子和引号明显未完成时，同样触发导演续补。

`[DONE]` 或明确的 `finish_reason` 是模型流的完成依据。另一个层级是本应用的 SSE `done` 事件：它确认服务器已完成本次结果处理。浏览器必须收到这个事件，才能进入正常完成流程。

结构化 JSON 仍保留原有的“首个完整对象提前停止读取”机制，后续还有领域验证。这种方式减少本地模型闭合 JSON 后继续输出解释的风险；它没有等待整个供应商响应的最后事件，属于与正文流不同的协议策略。

### 4.3 输入绑定的持久化续写

`app/writing/prose_recovery.py` 负责接收、检查点和续补；导演运行时通过回调负责数据库保存及任务状态。

检查点记录正文、输入哈希、完成标记和原因。哈希包含完整消息、模型、提供商、地址、输出与上下文预算、采样和思考设置；检查点不保存 API Key。路线、约束、正文上下文或模型配置改变后，旧流回执不再复用。

中断后续补会显式提供已保留片段和断点锚点，限制继续执行当前任务，禁止重新介绍人物、复述已完成动作或引入下一章事件。拼接会去掉较长的精确前缀回声，半句断点直接接续，完整句末保留段落边界。

默认一次接收流程最多 3 次尝试，可配置为 1–5 次。传输层在尚未输出正文时仍有自身 HTTP 重试；这个次数不是全部底层 HTTP 请求数量上限。耗尽后保留检查点并暂停，避免无限续补。

首个片段立即保存，正常接收时随新片段到达约每两秒保存；暂停、中断、失败和完成时立即保存。任务状态检查限制为接收过程中约每 0.25 秒一次，并在完成前重新检查，减少逐 token 读取完整任务记录的开销。进程被突然终止可能损失最近一次保存后收到的片段。保存完成回执后，仍要通过既有正文审校、接纳和记忆结算；它不代表作品已经通过文学判断。

### 4.4 保留硬约束与完整方法

`app/writing/context_builder.py` 的必需区块不再受一般字符上限截断。最近正文仍按原有策略保留有限尾部；局部改写仍使用精简任务配方。可选方法区块使用完整 Skill 单元，其步骤和正反例共同进入或共同省略。

`injected` 标记由完整方法块是否存在判断。提示词版本更新后，回归案例也显式更新版本断言；其他事实边界断言保持有效。

这种方式的代价是大型硬约束可能让某些以前“勉强发送”的请求被阻止。解决方式是作者调整任务范围，或选择实际支持更大窗口的模型。偷偷删掉最后几条规则会让错误更难发现。

### 4.5 界面只在收到确认后进入完成状态

`static/js/core/stream.js` 独立处理流数据、完整事件边界和服务器错误。支持分片 UTF-8、LF/CRLF 和多行 data；不把未封闭的最后一条事件当作有效确认。

普通生成遇到提前 EOF 时保留右侧已经显示的正文片段，并显示失败或停止；不会走“生成成功”的候选版本登记流程。这里保留的是当前页面中的片段，尚不等同于数据库中的导演检查点；关闭页面可能丢失未登记的手动生成片段。

服务器明确返回 `needs_review` 时，界面显示“候选稿已保留 · 需复核”，登记为 `generation-needs-review` 来源。它仍是候选稿，后续沿原有流程由作者决定是否采用。

两份修改后的浏览器脚本增加资源修订标记，防止同一应用版本下复用旧缓存。本轮未生成或发布新的安装包。

### 4.6 段落清理保留创作节奏

续补去重原先先将每个句子去掉首尾空白，再拼接，导致原有段落消失。本轮保留原始句子单元，仅在比较重复内容时移除空白。长度门槛和相邻精确重复条件仍然生效，不因短句重复而大范围删除正文。

## 6. 下一轮适合继续优化的方向

### 6.1 首先建立真实长篇评测基线

选择历史、悬疑、关系或观察型叙事的固定作品样本，准备明确的作者要求、事实证据、人物知情边界和章末状态。对照保持模型、设置、目标字数与素材一致；记录单次失败、续补次数、费用和作者最终修改量。

自动检查应关注未来信息泄漏、无来源新增事实、人物位置和知识矛盾、重复段落、计划漏交付与完成判定。作者盲评关注因果推进、人物行动可信度、对白辨识度、信息揭示、段落节奏和结尾体验。机械检查分不能替代文学评分。

建议先建立少量高质量案例，再扩大数量。优先关注“恢复后是否比中断前更啰嗦、是否重复场景结果、是否引入额外事件”，这比一个总分更能定位长篇问题。

### 6.2 全书规划与记忆抽取按输出容量分批

为角色卡、卷级规划、章节路线、原子事实设计独立批次及合并契约。输出容量不足时减少条目数量；不能只增加 max_tokens。跨批合并必须检查稳定 ID、顺序、章数、重复实体和事实证据。

验收目标：较小窗口模型也能交付完整批次；失败只重试当前批次；每批保留输入版本、输出校验结果和完成回执。

### 6.3 统一普通生成与分场生成的上下文规则

当前可选导演分场模式会重新构造紧凑上下文，使用独立规则与检索逻辑。它与标准提示词配方仍存在重复，完整 Skill 取舍也不能自动保证该分场最终请求采用相同配方。应明确保留必须的作者约束、正典和人物边界，同时只暴露当前分场可执行的路线内容。

验收目标：相同作者硬约束在两种生成方式中都完整可见；后续分场事件不会因整章反馈提前暴露；不能用“已由导演校验”替代模型本轮实际需要遵守的禁令。

### 6.4 完成章节候选检查点的来源绑定

本轮新增流回执已经绑定完整输入。原有 `chapter_draft_checkpoint` 主要按章节 ID 恢复，之后再审计。若作者在暂停期间修改了路线或硬设定，仍可能拿到旧候选进行审计。

下一步应为完成候选补充明确的来源版本与约束指纹。发生冲突时保留旧候选为历史版本，显示来源已变化，重新审查或生成当前任务；不能静默接纳旧结果。应兼容旧任务，并测试作者编辑、路线修订、事实重建三种变更。

### 6.5 手动生成的中断片段也获得持久化草稿

当前导演流已有数据库检查点，普通生成的失败片段仍主要保留在页面。可以增加独立的中断草稿登记，绑定作品、章节、原文版本和模式，标明未完成。它应允许复制、继续和丢弃，但不能自动进入正式正文或记忆。

验收目标：刷新后能恢复片段；切换作品不会误存到新作品；版本冲突时保留片段并让作者决定；失败和成功候选的状态清楚。

### 6.6 继续拆分导演运行时与前端全局状态

本轮只提取了正文恢复，导演运行时仍承担许多阶段。后续适合逐步拆出计划准备、候选审校、正文接纳、记忆恢复和发布体检，用明确的输入输出连接阶段。前端可以先让生成状态拥有单一对象，再逐步减少全局变量共享，不需要一次引入完整构建体系。

验收目标是现有接口、作品格式与恢复结果保持兼容，同时每个阶段可以单独模拟失败并验证保存顺序。拆文件数量本身不是完成标准。

## 7. 应保留的产品方向

InkForge 适合继续围绕中文长篇作者的工作建立优势：章节事实边界、人物知情、因果和场景交付、对白声音、证据审校以及作者取舍。DeepWrite 的通用智能体平台、文件工作区和素材整理能力可以作为机制参考，是否引入工具执行、多智能体或更重的桌面框架，应由实际创作任务决定。

本轮交付的是经过失败场景验证的代码优化与对照报告。后续评测应回答一个具体问题：在相同作者意图与事实材料下，作品能否更稳定地交付完整、连贯、少重复且可审阅的章节。
